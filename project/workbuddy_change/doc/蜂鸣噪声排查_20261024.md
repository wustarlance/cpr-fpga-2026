# HDMI 音频"蜂鸣"噪声排查

> 2026-10-24。现象：音乐正常播放，同时叠加类似蜂鸣的高频噪声。

---

## 一、结论：首要嫌疑是 44.1 kHz 素材走了"最近邻"重采样

`pcm_player.v` 第 76–125 行是这么做的：

```verilog
localparam integer FS_OUT = (MCLK_HZ + 128) / 256;   // 48000
wire [19:0] W_acc_sum  = S_acc + I_sample_rate[18:0];
wire        W_acc_over = (W_acc_sum >= FS_OUT);
```

每来一个 48 kHz 帧，`S_acc += fs_in`；只有累加值超过 48000 才从 FIFO 取一个新样本，否则**重复上一帧的值**。这是零阶保持（zero-order hold），不是插值。

我用等幅 1 kHz 正弦跑了三种情况的量化对比：

| 素材 | 处理方式 | 实测 SNR | 说明 |
|---|---|---|---|
| 48 kHz | 1:1 直通 | **250 dB** | 每帧取一个样本，无任何重采样 |
| 44.1 kHz | 最近邻（**当前**） | **27.7 dB** | 噪声只比信号低 27 dB，明显可闻 |
| 44.1 kHz | 线性插值 | 62.4 dB | 改善 35 dB |

44.1 kHz 时取数比例为 0.9187，**保持间隔在 12 帧和 13 帧之间交替**（实测 12 帧出现 2430 次、13 帧 1079 次）。这个交替模式的周期是 160 帧：

```
44100 : 48000 = 147 : 160
```

于是叠加了一个 **48000 / 160 = 300 Hz** 的周期性调制。同时零阶保持会生成输入频率的镜像分量：1 kHz 在 44.1 kHz 采样下的镜像为 43.1 kHz 和 45.1 kHz，折叠进 48 kHz 的带内后落在 **2.9 kHz 和 4.9 kHz**——听起来就是尖锐的哨音/蜂鸣。

宽频音乐更糟：每个频率成分都产生自己的镜像，叠成一层密集的高频嘶嘶声。

### 怎么确认

```bash
python workbuddy_change/tools/check_wav.py <你的素材>.wav
```

采样率 44100 会直接报 `[!!]` 并说明后果。

### 三个修法

| 方案 | 改动量 | 效果 | 代价 |
|---|---|---|---|
| **A. 换 48 kHz 素材** | 零 | SNR 250 dB，彻底消除 | 需要重新转码+烧卡 |
| **B. 改线性插值** | ~20 行 | 62.4 dB | 需要一个乘法器，DSP 还剩 4 个 |
| C. 真跑 44.1 kHz | 大 | 无损 | 要改 PLL（11.2896 MHz）、ACR_N=5645、核参数 "44K" |

**建议先做 A 验证**：如果能确认换成 48 kHz 后噪声消失，就说明诊断成立，再决定要不要为兼容 44.1 kHz 而做 B。

## 二、次要问题：`MCLK_HZ` 参数与实际 PLL 频率不一致

顶层 `rtl/top_tf_hdmi_audio.v` 第 387 行注释写得很清楚：

```verilog
.clk2_out   (audio_mclk)        // 12.295082 MH, 音频 + ADC
```

实际音频主时钟是 **12,295,082 Hz**，不是 12.288 MHz。

但第 754 行的例化没有覆盖 `MCLK_HZ`：

```verilog
wav_audio_sd_top #(
    .START_SECTOR (32'd12000),
    .ACR_N        (6144)
) u_audio_wav (
```

于是模块内部用的是默认值 `MCLK_HZ = 12_288_000`，`pcm_player` 算出 `FS_OUT = 48000`；而 `pcm_frame_tick` 按 256 分频，**实际帧率是 12295082 / 256 = 48027.66 Hz**。

影响分两档：

- **对 48 kHz 素材：无影响。** 每帧都取一个样本，1:1 直通，帧率略高只是播放速度快 0.0576%（1 音分，人耳不可辨）。
- **对 44.1 kHz 素材：音调额外偏高 0.0576%。** 相比重采样本身的 27.7 dB 噪声，这是次要的。

但还有一个连带问题：`ACR_N = 6144` 声明 48.000 kHz，而实际帧率 48027.66 Hz。好在 `audio_arc_calculate` 是用**计数测量**实际间隔的（每 48 个音频帧发一次 ACR，得到 CTS≈25160），接收端据此恢复出约 48028.6 Hz，与真实帧率只差 0.94 Hz。这个设计自己修正了大部分偏差，但理论上每约 1.06 秒会滑过一个样本，可能产生极轻微的偶发爆音。

**修法**：例化时补 `.MCLK_HZ (12_295_082)`。注意 `FS_OUT` 变成 `(12295082+128)/256 = 48028`，44.1 kHz 素材的播放速率才真正等于 44100 Hz。

## 三、隐患：`audio_gate` 会把音乐切碎（仅 `app_mode == 2` 时）

`rtl/top_tf_hdmi_audio.v` 第 309 行：

```verilog
wire audio_gate = (app_mode != 2) || (beat_hold_ms != 0);
...
.I_audio_left_data  ((ENABLE_AUDIO && audio_gate) ? audio_left_data : 24'd0),
.I_audio_right_data ((ENABLE_AUDIO && audio_gate) ? audio_right_data : 24'd0),
```

这是原来"音调发生器 + 训练模式节拍器"时代的逻辑：只有按压后 `beat_hold_ms = 40`（40 ms）的窗口内才放行声音。

**音源已经换成 WAV 音乐了，这个门控没有存在意义，而且有害**：

1. 数据被清零，但 `.I_audio_valid(audio_output_valid)` **不受门控**，照样每帧拉高
2. 在 `app_mode == 2` 且没有按压时 → 48 kHz 帧全部发送 0 → 音乐消失
3. 按压时 40 ms 内有声、之后又归零 → 音乐被切成 40 ms 的碎片，听感是"突突"的断续噪声

如果上板时切到了模式 3（`app_mode == 2`），蜂鸣很可能就是这个造成的，而不是重采样。

**修法**：直接删掉 `audio_gate`，两行都改成

```verilog
.I_audio_left_data  (ENABLE_AUDIO ? audio_left_data  : 24'd0),
.I_audio_right_data (ENABLE_AUDIO ? audio_right_data : 24'd0),
```

或者至少让它同时门控 `I_audio_valid`，避免"有效帧里全是 0"。

## 四、隐患：ACR 输出在 valid=0 被清零，且第二个 always 无复位

`rtl/audio/audio_arc_calculate.v` 第 51–64 行：

```verilog
always @(posedge I_clk) begin        // ← 没有复位
    if(S_audio_valid_div) begin
        O_acr_valid <= 1'b1;
        O_acr_cts   <= S_acr_cts_cnt + 'd1;
        O_acr_n     <= ACR_N;
    end
    else begin
        O_acr_valid <= 1'b0;
        O_acr_cts   <= 'd0;          // ← valid=0 时把 CTS/N 清零
        O_acr_n     <= 'd0;
    end
end
```

两个问题：

1. **无复位**：上电后 `O_acr_valid` 等信号是未定义值，第一个 ACR 包之前的状态不确定。
2. **清零**：`CTS`/`N` 只在 valid 为高的那一拍有效。如果 HDMI 核内部对 valid 做了寄存（延迟一拍采样），读到的就是 `CTS=0, N=0`。接收端按 CTS=0 恢复时钟会得到荒谬结果，通常表现为周期性重同步噪声。

**修法**：改成保持最后值，并补引脚复位

```verilog
always @(posedge I_clk or posedge I_rst) begin
    if (I_rst) begin
        O_acr_valid <= 1'b0; O_acr_cts <= 'd0; O_acr_n <= 'd0;
    end
    else if (S_audio_valid_div) begin
        O_acr_valid <= 1'b1;
        O_acr_cts   <= S_acr_cts_cnt + 'd1;
        O_acr_n     <= ACR_N;
    end
    else begin
        O_acr_valid <= 1'b0;          // CTS/N 保持不变
    end
end
```

## 五、排查顺序（按成本从低到高）

| 步 | 操作 | 若噪声消失说明 |
|---|---|---|
| 1 | `python check_wav.py 素材.wav` 看采样率 | — |
| 2 | 换一个 **48 kHz / 16 或 24 bit / 立体声** 素材重烧 | 就是最近邻重采样 |
| 3 | 若素材已是 48 kHz，切到模式 1 或 2（避开 `app_mode==2`） | 就是 `audio_gate` 切碎音乐 |
| 4 | 拨 SW4 停止播放 | 只是定位：声音源是 WAV 还是 HDMI 底噪 |
| 5 | 拔掉 HDMI 线，看显示器本身有无噪声 | 排除显示端/音响自身 |

第 4 步很关键：**如果停止播放后蜂鸣仍在**，那问题不在音频数据，而在 ACR/数据岛（问题三、四），因为静音帧也会照常发送。

## 六、当前代码里确认**不是**问题的部分

| 检查项 | 结论 |
|---|---|
| PCM 跨时钟域（MCLK → 像素域） | toggle 握手 + 3 级同步，帧间隔 524 个像素时钟，不会漏帧 |
| 24 bit 对齐 | `S_aud_frame[23:0]` 左声道、`[47:24]` 右声道，与 reader 的左对齐约定一致 |
| `audio_arc_calculate` 的 ACR 频率 | AUDIO_DIV = 6144>>7 = 48，每 48 帧发一次，即 1000 Hz，远高于 HDMI 规范要求 |
| HDMI 核参数 | `AUDIO_SAMPLE_RATE="48K"` 与 ACR_N=6144 一致 |
| FIFO 欠载处理 | 会丢弃旧样本并填 0，不会重复最后一个采样值（那个才是典型"直流嗡"） |
