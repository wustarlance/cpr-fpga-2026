## 三、`.gitattributes` 为什么必须一起推

根因链条：

1. 仓库 `core.autocrlf = true`
2. `.gitattributes` 第 1 节有 `*.v text eol=lf`
3. 第 2 节把 `05_lab_ex/**`、`project/vendor/**`、`project/ip/**` 设成 `-text`（不转换）
4. **但 `project/rtl/HDMI/` 不在任何保护范围内** → 它匹配 `*.v text eol=lf`，CRLF 会被转成 LF
5. 加密核是 `pragma protect` + AES 密文，**换行符一改，密文字节就变**，解密必然失败

`.gitattributes` 注释里已经记着「2026-10-13 的 PR #2 无意中把 18 个文件从 LF 转成了 CRLF」——加密核损坏八成就是这么来的，不是谁手动改坏的。

本次新增一行，把规则收紧到按后缀判断，覆盖任何位置：

```gitattributes
*.enc.v           -text
```

验证方式（改完立刻可查）：

```bash
git check-attr text project/rtl/HDMI/hdmi_1_4b_transmitter_core_wrapper.enc.v
# 期望：... text: unset      ← unset 才表示不做任何转换
```

## 八、推送前最后两个检查

```bash
# 1) 加密文件都没有被转换（应全部 unset）
for f in $(git ls-files "*.enc.v"); do git check-attr text "$f"; done | grep -v unset
# 无输出 = 全部安全

# 2) 暂存区里加密文件的大小与工作区一致
git ls-files -s project/vendor/include/sdr_init_ref.enc.v
stat -c%s project/vendor/include/sdr_init_ref.enc.v
```

第 2 条的意思是：`.enc.v` 现在是 `-text`，暂存 blob 的字节数应当等于工作区文件字节数（`sdr_init_ref.enc.v` 应为 247 行对应的实际大小）。若两者差异明显，说明仍被当文本处理了。
