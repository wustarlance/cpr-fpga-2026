# TD 关键告警离线排查（2026-10-25）

本轮已完成当前实现的物理查询、位置约束实验和最小工程对照，**三类关键告警仍未关闭**。产品每个顶层原有7条记录：PHY-7002 三次、PHY-5079 一次、USR-6135 三次；它们属于三类问题，不能将重复诊断次数当成独立故障数。

使用用户现有 TD **6.2.168116 / EG4S20BG256**，以 `1297d6e6336a814d2d172e306a29c53399c4be50` 的已路由产品为基线。全部产品设计输入仍与 `verify_20261025T071736.335593Z` 的哈希一致，两个产品路由检查点采集前后哈希不变。没有修改产品 RTL、PLL、频率、引脚或 SDC，没有重新生成产品位流，没有上板。

该产品基线的 setup 为 +0.120 / +0.159 ns、hold 为 +0.003 / +0.004 ns，内部 TNS 为0。它们是此前完整构建的结果，本轮没有将诊断工程的结果替代产品时序。严格检查仍 failed；这是项目的工程门禁，不是主办方对作品的判定。

## 实际排查结果

| 类别 | 本轮证据 | 结论 |
|---|---|---|
| USR-6135 | 两顶层三个 PLL 的反馈端点已完整采集；整体网被标为 global，反馈分支报告2.099 / 2.231 / 2.099 ns | 不能由 global 标签推断末段专用反馈资源或补偿可靠性，告警未关闭 |
| PHY-7002 | 实际宏位置确认；同位置固定约束被接受，IsFixed=True，但完整项目仍在增量布局报错；23 LUT / 32寄存器小工程也复现 | 单补位置约束不能修复，需厂家解释硬宏的 ECO 合法性检查与合法定位方式 |
| PHY-5079 | 当前产品相移时钟到内置 SDRAM 时钟 PAD 的分支仍有1段本地布线；不含 PLL 的小工程同样复现该类告警 | 不是只出现在 CPR 或 WAV 逻辑中；需要受支持的转发时钟结构与完整时序模型 |

### PLL：补齐之前缺少的视频反馈端点

本轮对 `top` 和 `top_adc` 的实际路由检查点分别查询，去掉 ADC 的 `u_board/` 前缀后：

| 反馈端点 | NetDelay |
|---|---:|
| sys_pll_m0/pll_inst.fbclk | 2099 ps |
| video_pll_m0/pll_inst.fbclk | 2231 ps |
| u_audio_pll/pll_inst.fbclk | 2099 ps |

三个网的驱动器均为 `EG_PHY_GCLK`，整体 `Route Type=global`。报告中反馈端点 slack 为 `inf`，不能将它解释为补偿相位通过验收。此前只打印前8个负载时没有取得视频 PLL 的端点，本轮已完整取得。

10月23日的三 PLL 最小实验不再重复执行：其三个生成包装器与当前产品逐字节相同，工具二进制 SHA256 也相同，旧实验仍有三个 USR-6135。结构化记录明确区分本轮实际物理查询与历史最小实验复用。

不采用单纯切换 No Compensation 的方式消警：它会改变相位补偿条件，不能沿用当前跨时钟关系和 SDRAM 捕获结论。相关模式依据仍是本机 TN305_1.1 PLL 用户指南第3页。

### SDRAM 宏：坐标和受控实验

`report_cells` 基本属性可安全读取，确认宏模型为 `EG_PHY_SDRAM_2M_32`，物理坐标 `x=164,y=288`，网格 `col=20,row=36`、offset=0。物理坐标、网格坐标和 PNL 的 `x20y36_0` 不是同一种写法。

安路[官方 FAQ 的位置约束示例](https://tech.anlogic.com/Cn/Index/index/cate/32/tp/1/p/2.html)使用 `set_inst_assignment` 和 `x…y…z…` 格式。本轮位置值取自该器件实际报告，实验约束为：

```tcl
set_inst_assignment {U3/sdram} {location = x20y36z0;}
```

将其应用于产品的门级检查点后，TD 确认约束，最后报告 `IsFixed=True`，却仍在 ECO / incremental legalization 阶段记录三次 PHY-7002，分别涉及初始 `(12,12)` 和实际 `(164,288)`。因此未把这条约束加进产品。

另一受控实验仅将手册列出的 `place opt_timing` 从 high 改为 off。PHY-7002 从三条减少为一条，但仍有增量合法化和首条重定位诊断；这是重复执行次数减少，不是修复了两个独立问题。该实验只做布局，估算 setup +0.557 ns、hold −0.011 ns，不能作为最终路由时序，也未采用为产品配置。

“可能与 ECO 对内置硬宏的处理有关”是基于上述日志的推断，不能直接称为已确认的软件误报或宣称可以豁免。

两个计数器配置都真实完成综合、布局、布线和诊断报告，固定配置仍报宏重定位。PHY-5079 记录两次是因为脚本在 `route` 内检查一次、随后显式 DRC 再检查一次，均指向同一条本地时钟分支。

计数器案例与零计数器对照的其余四个输入文件逐字节相同，包括同一高强度布局脚本、引脚、时钟与位置约束文件；只有 `probe.v` 不同。因此无需产品的 SD 卡、音频、教程或加密 SDRAM 控制器即可复现两类问题。它说明这些应用模块不是复现告警的必要条件，不说明真实读写或板级时序已经通过。

所有小工程都未运行 bitgen、未上板，没有实际 SDRAM 初始化或读写流程。零计数器对照没有实际用户时钟负载，其零告警不能替代产品验收。
