# HX4S20C 横线诊断：D107

适用：HX4S20C V1.0、EG4S20BG256，沿用主工程的引脚表及实际 PLL 配置。诊断入口为 `top_sdram_diag`。这是独立的测试工程，产品 `top` / `top_adc`、缓存调度、训练 UI、SD 内容和约束均未修改。

## 这次要区分什么

实际屏幕仍有横线，且重新启动后位置改变。GitHub main `c8f2ab93601ccbea23d1418084333b3680622100` 已包含 PR #5 的刷新互锁和后续缩放时序修正。因此不能继续把“刷新互锁仿真通过”当作横线已解决。

本诊断同时执行两个独立操作：

1. 视频时钟域直接生成竖向色块，经现有 RGB→AXIS、HDMI 核和 PHY 输出。色块数据不经过 TF、缩放器、帧 FIFO 或 SDRAM。
2. 保留实际 40 MHz / 180° SDRAM 时钟及自动刷新，通过实际 `sdram` / `sdr_as_ram` / 片内 SDRAM，逐字验证全部 2,097,152 个 32 位字（8 MiB）。

SDRAM 每轮依次写全零、全一、地址相关数据及其反码。每种图案写完等待 100 ms，再完整读两遍，中间不重写。检测首个数据不符、缺失响应、无请求响应及初始化超时；结果保持至复位。不使用 `Sdr_busy` 作为背压（该接口手册将其标为暂未使用）。

突发起点四字对齐，开始前等待初始化完成和刷新空闲；开始后保持整段连续。此项遵循 APUG011 的“正常读写过程中不需管理刷新”约定，与产品现有每拍刷新门控不同，也是一次有意的隔离实验。诊断通过不能独自证明产品仲裁或连续混合读写已经正确。

本测试覆盖易失性 SDRAM 全空间；不访问 TF 内容，不包含 TF 写操作。显示不使用读回数据，所以“色块正常”和“SDRAM 检查通过”是两个单独结果。

## 拨码及显示

先设置 SW1，再复位或断电重启。SW1 在初始化结束时锁存，本次运行中改变它无效。

| 操作 | 含义 |
|---|---|
| SW1=0 | 每段 256 字，与产品默认长度一致 |
| SW1=1 | 每段 128 字，作为对照 |
| SW2=0 | A 组显示页：结果本身 |
| SW2=1 | B 组显示页：计数页（2026-10-19 新增） |
| SW4/SW3=00 | A 组：显示 `D107SPF0`：固定编号、状态、图案编号、错误类型 |
| SW4/SW3=01 | A 组：首个错误的 **32 位字地址**，八位十六进制；字节地址=该值×4 |
| SW4/SW3=10 | A 组：首个错误的期望 32 位数据，八位十六进制 |
| SW4/SW3=11 | A 组：首个错误的实际 32 位数据，八位十六进制 |
| SW4/SW3=00 | B 组：**`head_map`** —— 第 k 位 = 图案 2 第一次读回时第 k 个字是否正确 |
| SW4/SW3=01 | B 组：图案 2 第一次读回的**不符字数** |
| SW4/SW3=10 | B 组：图案 2 第二次读回的**不符字数** |
| SW4/SW3=11 | B 组：最后一个不符字的 32 位字地址 |

### 为什么要有 B 组

图案 0/1 每个字都相同，任何丢字、错位、相邻地址混叠都看不出来 —— 所以“全零/全一通过”不构成证据。图案 2 是第一个每个字都不同的图案，只有它会暴露问题。但只报“首个错误”无法区分后果完全不同的几种机制：

| `head_map` | 不符字数（单次读回） | 结论 |
|---|---|---|
| `AAAAAAAA` / `55555555` | 1 048 576 | 一半字错且隔字交替 ⇒ **地址位混叠**，某个地址位没接/没解码 |
| `00000000` | 2 097 152 | 每个字都错 ⇒ **读回流水线整体偏移一个字**，或首个响应被吞 |
| `FFFFFFFE` | 4096（=16 段×256 字） | 只有每段第一个字错 ⇒ **突发首字被吞** |
| 零星某几位为 0 | 很小 | 真正的存储单元缺陷/保持力问题，且位置有物理含义 |

`head_map` 只在图案 2 第一次读回采集；并且**不再在“首个不符”处立即停机**，否则第二个数永远数不出来。`S` 因此要等整个图案 2 跑完才落到 `E`，数码管停在 `E` 的时间会比以前长一点。

若读回确实整体偏移，最后一次读回应答不会到来，看门狗仍会结束测试，但已经记录好的首个错误不会被超时信息覆盖（旧版会把它改写成 `actual=00000000`，等于把证据毁掉）。

这里 SW1..4 对应主工程 `dip_sw[0..3]`。0/1 表示逻辑电平，按实际板上拨码方向确认。切换 SW2/SW3/SW4 后等待数码管稳定再记录；它们只改变查看内容。

`S` 状态：0 等待初始化，1 写入，2 等待保持，3 读回，4 全部通过，E 数据错误，F 超时或协议异常。

`P` 图案：0 全零，1 全一，2 地址相关数据，3 地址相关数据反码。`F` 错误类型：0 无，1 数据错误，2 超时，3 多余/无请求响应。例如 `D1074300` 表示全部通过，最后图案为 3。

LED1=SDRAM 初始化完成；LED2=正在测试；LED3=全部通过；LED4=失败。数码管结果全部留在 SDRAM 时钟域，无多位总线逐位同步。视频域只同步稳定的成功/失败单比特标志。

视频：测试中为蓝色色块，成功后为绿色色块，失败后为红色色块。只应有竖向色块边界，启动时的颜色切换稳定后不应出现白色横线。

## 板上记录及下一步

先用 SW1=0，至少进行三次完整断电重启；每次等待数码管停在 4/E/F，并记录下表。再以 SW1=1 重复。通常测试在数秒内完成；初始化缺失也会在约两秒后报告 F。

2026-10-19 第一次实测（SW1=0，未接 HDMI）：

```
SW4/SW3=00  d107E210        S=E 数据错误, P=2, F=1 数据不符
SW4/SW3=01  00000000        首个不符的字地址 = 0
SW4/SW3=10  5AeC911E        首个不符的期望数据
SW4/SW3=11  5A3C991F        首个不符的实际数据
```

按 `pattern(2,a) = {a, ~a[10:0]} ^ 32'h5a3c96e1` 反解：

- `pattern(2,0) = 5A3C911E`，`pattern(2,1) = 5A3C991F`。
- 实际读回值**恰好等于地址 1 的数据**，说明硬件在被告知地址 0 时实际访问了地址 1。
- 而 `5AEC911E` 在 2²¹ 个地址里**不存在**对应的 `pattern(2,·)` 值（已穷举），所以这一个数以 `3`→`E` 记错；正确的期望值是 `5A3C911E`。重新读这一页时注意数码管扫描残影。

也就是说：**在最简单的访问形式下（突发四字对齐、纯写后纯读、不交织、只有一种数据流）地址就已经错开了。** 这不是仲裁或混合读写造成的，因为该诊断工程里根本没有帧 FIFO、没有 SD、没有读写交织。

B 组两个计数页正是为了分开剩下的可能机制，见上表。

| 次数 | SW1 | 色块横线 | A 组状态字 | 首个错误地址 | 期望 | 实际 | B 组 `head_map` | B 组不符字数 1/2 |
|---|---|---|---|---|---|---|---|---|
| 1 | 0 | | `d107E210` | `00000000` | `5A3C911E` | `5A3C991F` | | |
| 2 | 0 | | | | | | | |
| 3 | 0 | | | | | | | |
| 4 | 1 | | | | | | | |
| 5 | 1 | | | | | | | |
| 6 | 1 | | | | | | | |

- 色块正常、SDRAM 报 E/F：故障可在没有 SD/缩放/帧 FIFO 时重现，优先检查实际 SDRAM 控制器、时钟和初始化/刷新。错误数据与地址是下一次定位依据。
- 色块有横线、SDRAM 检查通过：优先检查直接视频至 HDMI 的输出链，不能归因于图片文件。
- 两项均正常、恢复产品后有横线：继续检查产品混合读写仲裁、FIFO/加载时序和 TF 数据。独立测试没有复现并不排除这些条件下的 SDRAM 问题。
- 两项均异常：保留两组现象，先核对诊断编号、位流哈希、工具版本和完整构建验收结果。

拍摄数码管四个查看页及屏幕即可，不必修改或重写 TF 卡。B 组请连同 SW2 的位置一起拍。

## 仿真边界

```sh
python tests/sim/run.py tb_sdram_bist tb_frame_roundtrip
```

`tb_sdram_bist` 校验测试引擎的地址、四图案、两种突发长度、重复读、故障锁存、超时和中途复位；它使用 ERAM 行为模型，不能验证加密控制器和实际存储阵列。

`tb_frame_roundtrip` 使用**仓库实际生成的两个 FIFO RTL**，核对四槽共 5120 个像素，包含 640 像素跨行纵向翻转、生产者背压、刷新等待、40/100/25 MHz 三时钟及读 FIFO 的实际同步输出延迟。SDRAM 控制器仍为十拍有序响应模型。本项没有仿真 HDMI 模拟电气行为，也不能替代板上记录。
