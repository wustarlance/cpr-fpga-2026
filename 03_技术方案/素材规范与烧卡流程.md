## 一、素材硬性要求（每条都有出处）

| # | 要求 | 出处 / 依据 |
|---|---|---|
| 1 | **格式必须是真 BMP**（不能把 PNG/JPG 改后缀） | 厂商《代码说明.md》注意事项 1 |
| 2 | **分辨率 640 × 480**（且四张必须**完全一致**） | `bmp_read.v` 的 `header_match`：`width[15:0] == bmp_width && height[15:0] == bmp_height` —— **精确匹配** |
| 3 | **24 位、无压缩**（`bit_count == 24 && compression == 0`） | 同上 `header_match` |
| 4 | **宽度必须是 4 的倍数** | `bmp_read` 不处理行末填充字节（第4站的坑）；640 天然满足 |
| 5 | **⭐ `biHeight` 必须为正（自下而上 bottom-up）** | 见下节 —— 这是**最容易被忽略、也最致命**的一条 |
| 6 | 建议 TF 卡格式化为 **FAT32** | 厂商《代码说明.md》注意事项 3（FPGA 不解析 FAT，但扫描到的是 FAT32 数据区） |

### ⚠️ 第 5 条为什么致命：`biHeight` 的符号会被 `header_match` 检查

`bmp_read.v` 第 73 行：

```verilog
(height[15:0] == bmp_height) &&   // bmp_height = 16'd480
```

而 `biHeight` 是从偏移 22 开始的 **32 位有符号小端整数**：

| 素材类型 | `biHeight` 的值 | 低 16 位 `[15:0]` | `== 480`？ | 结果 |
|---|---|---|---|---|
| **自下而上**（bottom-up） | `+480` = `0x000001E0` | `0x01E0` = 480 | ✅ | 正常找到 |
| **自上而下**（top-down） | `−480` = `0xFFFFFE20` | `0xFE20` = 65056 | ❌ | **`header_match` 不成立 → 这张图永远扫不到** |

**所以：用了 top-down 的 BMP，症状是"这张图根本不出现在轮播里"，而不是"显示反了"。** 很难往格式上想，所以必须提前卡住。

### 权威依据：`biHeight` 是谁决定的？

**是"写这个文件的软件"决定的**（它是文件头里的一个字段，由编码器填写）：

- 微软官方文档《[Top-Down 与 Bottom-Up DIB](https://learn.microsoft.com/zh-cn/windows/win32/directshow/top-down-vs--bottom-up-dibs)》：
  > "在自下而上 DIB 中，图像缓冲区以像素底行开头……**内存中的第一个字节是图像的左下角像素**。在 GDI 中，所有 DIB 都是自下而上。"
  > "**如果 `biHeight` 为正，则图像为自下而上。如果 `biHeight` 为负值，则图像是从上到下。**"

- **本工程的实际决定者**：厂商的 `convert_images_to_bmp.py` 用的是 **Python Pillow（PIL）**，它 `save(path,'BMP')` 写出来的是**自下而上（+480）**。

### 🔬 实测证据（本项目全部 BMP）

| 文件 | `biHeight` |
|---|---|
| `doc/TF卡图片/A_工程适配版.bmp` | **+480** |
| `doc/TF卡图片/logo_640x480_24bit_不翻转.bmp` | **+480** |
| `doc/TF卡图片/苹果/草莓/西瓜_..._工程适配版.bmp` | **+480** |
| `doc/convert/1.bmp`、`3.bmp`、`output_bmp/*.bmp` | **+480** |

**全工程 11 张 BMP，无一例外都是 +480。** 没有 top-down 的样本。

> 📌 **关于 `logo_..._不翻转.bmp` 这个文件名**：从数据上**无法确定**它的命名意图（它的 `biHeight` 也是 +480，和其它图一样，也不与任何图构成镜像关系）。
> **实践结论：判断素材是否合规要看 `biHeight` 的符号，不要看文件名。**

### 🔬 `WRITE_V_FLIP` 为什么"肯定是翻转的"

两层理由：

**① 素材侧不翻转（实测）**：把源 PNG 按脚本的方式缩放到 640×480，与生成的 BMP **逐字节完全相同**：

```
doc/convert/1.png  vs  1.bmp  →  完全相同（未翻转）✅
doc/convert/3.png  vs  3.bmp  →  完全相同（未翻转）✅
```

→ 转换脚本只做"**缩放 + 存成 24 位 BMP**"，**不做任何上下翻转**。

**② 硬件侧必须翻**：素材是自下而上（第 0 行 = 图像最下），而显示从上往下扫（第1站）。两边方向相反，**不翻必然上下颠倒**。

**③ 而且它是编译期参数**：`parameter WRITE_V_FLIP = 1`，不是运行时信号。取 1 时三目运算符永远走翻转分支，**不翻转的那条分支会被综合器直接优化掉** —— 所以硬件里**确实只实现了翻转那一条路径**。

> 补充：**读引擎不需要翻转**（`frame_fifo_read.v` 里没有对应逻辑）。写侧翻过了，读出来就是正的。这套配合是固定的，不要单独去改其中一个。

### 2.2 `sync_to_sd.py`（烧卡）—— ⭐ 它解决了一个很隐蔽的坑

**为什么需要它**（厂商 README 原文）：

> 在向 FPGA 用的 SD 卡拷贝新图片时，直接在电脑上"删除旧图片再拷贝新图片"往往**无效**。因为普通删除操作只会清除文件系统记录，而 FPGA 是采用"**物理扇区扫描**"的，**残留在底层扇区里的旧图片依然会被 FPGA 识别**，导致显示旧图或直接死机卡死。

**它做三步**：

| 步 | 动作 | 作用 |
|---|---|---|
| 1 | **把卡上所有 `.bmp` 开头的 `BM` 魔数改写成 `XX`** | 破坏旧图的识别标志 → FPGA 扫描时会跳过这些残留数据 |
| 2 | 从文件系统层面删掉所有可见文件/文件夹 | 腾空间 |
| 3 | 从 `output_bmp/` 取最多 4 张，**加数字序号前缀**后拷入 | 序号前缀让 FAT32 倾向连续分配 → FPGA 物理扫描时能**快速连续**读到 |

> ⚠️ **注意：它不做"裸写扇区"**。素材仍然是通过文件系统（FAT32）正常拷贝的 —— 真正解决问题的是**第 1 步破坏魔数**。

### 2.3 ⚠️ 这两个脚本都是 Windows 写法，需要移植

`sync_to_sd.py` 假设盘符形式：

```python
parser.add_argument('drive', help='SD 卡所在的盘符 (例如: E: 或 E:\\)')
...
if not target_drive.endswith(':\\') and not target_drive.endswith(':/'):
    if target_drive.endswith(':'):  target_drive += '\\'
    else:                            target_drive += ':\\'
```

**在 Linux 上直接传挂载点会坏掉**：比如传 `/media/starlance/SDCARD`，它不以 `:\`/`:/` 结尾、也不以 `:` 结尾 → 会被追加 `:\`，变成 `/media/starlance/SDCARD:\` → 路径不存在。

**移植要点**（很小，约 10 行）：

| 要改的地方 | 怎么改 |
|---|---|
| 盘符归一化 | Linux 下**原样使用传入路径**，不做 `:\` 补全 |
| C 盘拦截 | 换成拦截 `/`、`/home`、`/media` 本身这类危险路径 |
| 设备卸载 | Windows 上"安全弹出"，Linux 上建议 `sync && udisksctl unmount -b /dev/sdX1` |
| 权限 | 挂载点目录通常可写；若 FAT32 以 root 挂载需注意 |

> 💡 **另一个做法**：干脆**不用这个脚本**，在 Linux 下用"先 `mkfs.vfat` 重格式化整个卡 → 再按顺序 `cp` 四张图"的等效流程。重格式化天然解决了"旧数据残留"，比逐个破坏魔数更彻底。

## 三、烧卡流程（推荐）

```
① 用 convert_images_to_bmp.py 把四张原始素材转成 640×480 24bit BMP
        ↓
② 【检查】逐张核对：分辨率 640×480 / 24 位 / 非压缩 / biHeight = +480 / 宽度 4 的倍数
        ↓
③ 【清卡】重格式化为 FAT32（或运行 sync_to_sd.py 的破坏魔数 + 清空两步）
        ↓
④ 【写入】按顺序拷入四张图（加 00_/01_/02_/03_ 序号前缀）
        ↓
⑤ sync 后卸载
        ↓
⑥ 上板：上电应能扫到 4 张图并轮播
```

### 扫描耗时的账（重新核一遍）

| 情形 | 扫描扇区数 | 耗时（按 175 µs/扇区） |
|---|---|---|
| 图落在数据区起始附近（**清卡后新写入**的正常情形） | 约 2000 ~ 5000 | **0.35 ~ 0.9 秒** |
| 图落在卡的中后部（反复增删、碎片化后） | 约 100,000 | **约 17.5 秒** |

**结论**：**"先清卡再顺序写入"这一步不能省** —— 它同时解决了两个问题（旧的残影 + 扫描变慢）。这也是厂商脚本第 1、2 步存在的意义。

> 📌 **修正一条早先的建议**：之前我写的是"必须写**裸写扇区**脚本，让素材从扇区 0 开始"。**这个说法要改** —— 厂商的方案是**保留 FAT32 + 破坏旧图魔数 + 顺序写入**，比裸写更简单、且能直接在电脑上操作。**扫描代价靠"清卡 + 顺序写"来压低，而不是靠裸写。**

## 五、附：怎么检查一张 BMP 是否合规

**做法一：存成 `check_bmp.py`，然后带文件名运行**

```python
# check_bmp.py
import struct, sys
for f in sys.argv[1:]:
    d = open(f, "rb").read(64)
    if d[:2] != b"BM":
        print("%s: ❌ 不是 BMP（魔数不是 BM）" % f); continue
    w,    = struct.unpack("<i", d[18:22])
    h,    = struct.unpack("<i", d[22:26])     # ← 有符号！
    bits, = struct.unpack("<H", d[28:30])
    comp, = struct.unpack("<I", d[30:34])
    ok = (w == 640) and (h == 480) and (bits == 24) and (comp == 0) and (w % 4 == 0)
    print("%s: 宽=%d 高(biHeight)=%+d 位深=%d 压缩=%d 宽%%4=%d → %s"
          % (f, w, h, bits, comp, w % 4, "✅ 合规" if ok else "❌ 不合规"))
```

```bash
python3 check_bmp.py doc/TF卡图片/*.bmp          # 一次检查多张
```

**做法二：一行命令（把路径写在脚本里）**

```bash
python3 -c "
import struct,glob
for f in glob.glob('doc/TF卡图片/*.bmp'):
    d=open(f,'rb').read(64)
    w,=struct.unpack('<i',d[18:22]); h,=struct.unpack('<i',d[22:26])
    bits,=struct.unpack('<H',d[28:30]); comp,=struct.unpack('<I',d[30:34])
    print('%-46s 宽=%d 高=%+d 位深=%d 压缩=%d 宽%%4=%d' % (f,w,h,bits,comp,w%4))
"
```

**要看的四项**：

| 项 | 合格值 | 不合法会怎样 |
|---|---|---|
| 魔数 | `BM` | 扫描时直接跳过 |
| 宽 × 高 | 640 × 480 | `header_match` 不成立 → 扫不到 |
| `biHeight` 符号 | **正数** | 负数是 top-down → `height[15:0]` 对不上 → 扫不到 |
| 位深 / 压缩 | 24 / 0 | `header_match` 不成立 → 扫不到 |
| 宽 % 4 | 0 | 行填充被当像素 → 图像斜切 |

> ⚠️ 上面脚本里 `sys.argv` 的用法需要把文件路径作为参数传入；如果嫌麻烦，直接把 `f = "你的文件.bmp"` 写死也行。

## 6.2 买什么样的卡（最终规格）

| 项 | 结论 | 依据 |
|---|---|---|
| **容量** | **16 GB 或 32 GB** | 见下方 6.3 —— 32 GB 是"还能用官方 SDFormatter 格式化成 FAT32"的上限 |
| **类型** | **microSD **SDHC**（4~32 GB） | 参考工程 `sd_card_sec_read_write.v` 把 32 位值**直接**塞进命令：`cmd <= {8'd17, sec_addr, 8'hff}`，**没有 `<<9` 换算** → 假设**块地址(LBA)**，即 SDHC/SDXC。用 ≤2 GB 的老 SDSC 卡（字节地址）会读到完全错误的位置 |
| **速度等级** | **Class 10 / U1** | 不是为速度——SPI 模式上限只有 3.125 MB/s，Class 4 都远超。选 C10 只是因为**市面主流 + 有 SPI 实证的卡基本都是 C10** |
| **品牌** | **别买贵的**（这条是技术建议，不只是省钱）：优先 **朗科 / 爱国者 / 京东京造 / 海康** 等 15~30 元档；有 SPI 实证的是 **金士顿 32G C10**、**闪迪 Ultra 32G C10** | 见 6.3 与下方「品牌与渠道怎么选」 |
| **避开** | ① 闪迪 **Extreme** 等高速系列（贵，且 SPI 风险**更高**）② ≤4 GB 老卡 ③ 超低价"扩容卡" | 见 6.3 |
| **数量** | **先买 1 张！** 验证通过后再补第 2 张做备份 | 见 6.3 —— SPI 兼容性有真实不确定性 |
| **必备配件** | **USB 读卡器** | 卡槽在开发板**背面**；厂商同步脚本要求"卡已插入**电脑**"。现在笔记本基本无卡槽 |
| **卡内素材量** | 4 张 × 900 KB ≈ **3.6 MB** | 容量占用 <0.02%，完全不是约束 |

### 品牌与渠道怎么选（省钱路线）

**核心事实：在这个场景里，"便宜"和"能用"是同向的。**
lisy.dev 作者的原话建议就是"用**小容量、便宜的卡**"——因为**大容量、高速的卡恰恰最可能不再实现 SPI 接口**。
所以你不买贵卡不是在将就，而是在**规避风险**。

反例也有：Intenso 4 GB 就是"便宜但失败"。准确的说法是——**别为速度和容量付溢价**，而不是"越便宜越好"。

| 档位 | 品牌 | 32 GB C10 参考价 | 说明 |
|---|---|---|---|
| ⭐ **推荐** | **朗科 Netac / 爱国者 aigo / 京东京造 / 海康威视 / 大华** | 15~30 元 | 正经闪存厂，性价比好 |
| ✅ **有 SPI 实证** | **金士顿 Kingston 32G C10**、**闪迪 Ultra 32G C10** | 25~40 元 | 有实测可用记录（见 6.3） |
| ⚠️ **不建议为它加钱** | 闪迪 **至尊极速(Extreme)** / **至尊超极速(Extreme PRO)**、三星 EVO Plus 等高速系列 | 50 元+ | 贵，而且高速卡 SPI 风险**反而更高** |
| ❌ **不要买** | 拼多多/淘宝上 32 GB 卖 <15 元的 | — | 扩容卡/翻新卡，主控与固件不可控，SPI 兼容性无从保证 |

> 💡 **如果一定要闪迪**：买 **Ultra**，不要买 **Extreme**。
> lisy.dev 的实证可用卡正是 **SanDisk Ultra 32GB C10**。你觉得"闪迪贵"，看到的很可能是 Extreme/至尊高速系列。

**比品牌更重要的三件事**：

1. ⭐ **买"能退"的渠道**（京东自营 / 天猫旗舰店）。
   SPI 兼容性**必须上板实测**，万一同型号不行要能退换。**这一条的权重高于省 5 块钱。**
2. ⭐ **16 GB 或 32 GB，别超 32 GB**（理由见下）。
3. ⭐ **容量在这个项目里根本不是变量**：素材只有 3.6 MB。
   16 GB 和 32 GB 同价时随便挑，**别为容量加钱**。

### 为什么上限是 32 GB（这条最有价值）

官方的做法是「**使用 FAT32 格式化 TF 卡**」（例程文档原文），而且官方**随包提供 SDFormatter**。但：

> any SD card larger than 32GB is an SDXC card and has to be formatted with the exFAT filesystem. **the official SD Formatter tool will *always* format cards that are 64GB or larger as exFAT.** … The standard formatting tools built into Windows … only allow partitions up to 32GB to be formatted as FAT32
> —— [Raspberry Pi 官方文档 (sdxc_formatting.md)](https://raw.githubusercontent.com/raspberrypi/documentation/d256df52e038d8ded849aa78b8e232072ac94566/installation/sdxc_formatting.md)

推论链条：

```
买 32 GB 以内 (SDHC)
   → 官方 SDFormatter 一键就得 FAT32
   → 参考例程 lab_ex4_tf / lab_ex5_i2s 直接能跑 ✅

买 64 GB 以上 (SDXC)
   → SDFormatter 一定给 exFAT（官方要求 FAT32 ✗）
   → Windows 自带格式化也做不出 FAT32（上限 32 GB）
   → 得再去找第三方工具 guiformat.exe 折腾
   → 而你们在 Linux 上，还得多绕一层
```

**所以：32 GB 是这个项目最省心的容量，不要买 64 GB 以上。**

## 6.3 ⚠️ 一个真实存在的风险：SPI 模式兼容性

参考工程用的是 **SPI 模式**读卡（信号是 `sd_ncs` / `sd_dclk` / `sd_mosi` / `sd_miso`，SD_DAT3 当片选），不是 SD 4-bit 模式。而 SPI 兼容性**不是 100% 保证**的：

> 我用 **SPI 接口**实现 SD 访问，理论上所有 SD 卡都该支持。**但实践中发现，大容量、高速的卡已经不再实现 SPI 接口，或者实现方式不同。因此并不是所有 SD 卡都能在我的 FPGA 实现上工作。** 我的总体建议是用**小容量、便宜的卡**。
> ……已报告可正常工作的卡：Kootion 16G C10、Sandisk Ultra 32G C10、**Kingston 32G C10**、PNY Elite 32G、Patriot 64G C10、OUIO 8G C10 等。
> （Intenso 4G：**不要用**，品质已下降）
> —— [lisy.dev · Types of SD cards for FPGA boards](https://lisy.dev/sd-cards-types-for-fpga-boards.html)

**这条对采购顺序的直接要求**：

> 🔴 **先买 1 张，插上板子跑通官方例程 `lab_ex4_tf` 确认能读出来，再买第 2 张。**
> 不要一次买两张同型号——万一型号不兼容，两张一起废。

### 6.4.2 下单前在商品页核对这 5 项

| 核对项 | 应该是 | 不对会怎样 |
|---|---|---|
| 容量 | **32GB**（或 16GB） | 64GB+ → SDXC → 只能 exFAT，例程要求 FAT32 ✗ |
| 类型 | **microSD**（**HC**） | 标 **XC** 就是 ≥64GB，同上 |
| 速度等级 | **Class10 / U1** | A2/U3/V30 是高端高速款——**不必加钱，且 SPI 风险更高** |
| 卖家 | **京东自营** | 第三方店铺退货/正品都没保障 |
| 价格 | 32GB 在 **15~40 元** | <15 元基本是扩容卡/翻新卡；>50 元是高端款，不要 |

> 💡 **很多 TF 卡套餐自带 USB 读卡器**，买之前看一眼，别重复买读卡器。

> 📌 **关于"安防监控 / 行车记录仪专用"这类标签**（京东上极常见）：
> 这是**高耐久（循环写入寿命）**的营销词。你们总共只写 3.6 MB、几乎不重写，**这个特性用不上，等于在为它付钱**。
> 但它**不会有害**——这类卡往往正是"小容量 + 中等速度"，反而更符合"SPI 兼容性更好"的画像。
> 所以：**能用，但如果有同价位的普通款，选普通款。**

> 📌 **"读速 98MB/s / 160MB/s"这类数字对你们无意义**：SPI 模式下硬件上限就是 **3.125 MB/s**。
> 只要看到 **U1 / V10 / C10** 就达标了，**不必为更高的读速加钱**。
> 反过来，标 **U3 / V30 / A2** 的高端款才是该避开的（贵 + SPI 风险更高）。

### 6.4.3 读卡器怎么选

> 🟢 **先别买**：很多 TF 卡套餐**自带读卡器**。先看那张卡的套餐含不含，别重复买。

| 项 | 结论 | 理由 |
|---|---|---|
| 类型 | **SD/TF 二合一（双槽）** | 覆盖 TF 卡 + SD 卡套；"**双卡单读**"也完全够用，还更便宜 |
| 接口 | **USB-A + Type-C 双头**最省心 | 本项目的 Linux 机器有 **2 个 Type-C** 口；双头款在哪台电脑上都能用，不用找转接头 |
| 速度 | **USB 2.0 就够** | 全程只传 3.6 MB。但 USB3.0 现在也是白菜价，不必特意避 |
| 品牌 | **绿联 UGREEN / 川宇 Kawau / SSK 飚王 / 奥睿科 ORICO** | 15~30 元档就够，别买最便宜的杂牌 |
| ❌ 不要 | 多合一（CF/MS/XD）、需装驱动的、只读的 | 用不上，更贵、更容易坏 |
| ⚠️ 硬要求 | 必须是标准 **USB 大容量存储（UMS）** 设备 | 插上后 Linux 能看到 `/dev/sdX` 就是合格的；你们要用 `dd` 写裸扇区 |

搜索链接：[search.jd.com · 绿联 读卡器 二合一](https://search.jd.com/Search?keyword=绿联%20读卡器%20SD%20TF%20二合一) ·
[search.jd.com · 川宇 读卡器](https://search.jd.com/Search?keyword=川宇%20读卡器%20TF%20SD%20二合一)

> ⚠️🔴 **`dd` 安全警告（6.6 会用到）**——这是全项目最容易造成不可逆损失的操作：
>
> ```bash
> lsblk -o NAME,SIZE,MODEL,TRAN    # ① 插卡前执行，记下现有磁盘
> #    插入读卡器（含 TF 卡）
> lsblk -o NAME,SIZE,MODEL,TRAN    # ② 再执行，多出来的那个才是读卡器
> ```
>
> **`dd if=xxx.img of=/dev/sdX` 写错设备 = 直接抹掉系统盘 / 数据盘，无法撤销。**
> 辨认设备**用容量最可靠**：TF 卡 16/32 GB，系统盘几百 GB，不会认错。
> **绝不要凭 `/dev/sda` 这种猜测去写。** 写完记得 `sync` 再拔。
>
> ⚠️ **「双卡同读」读卡器会暴露两个 `/dev/sdX`**（SD 槽一个 LUN、TF 槽一个 LUN）。
> 这恰恰是 `dd` 最容易写错的场景——**别按名称猜，按容量认**：
> 插了 TF 卡的那个才有真实容量（如 29.7G），空槽那个是 0 B 或干脆不出现。
> 更稳的做法：**读卡器只插一张卡**，然后对照 `lsblk` 插拔前后的差集。

## 6.6 备份卡必须整卡克隆，不能拖文件复制

由于**方案修订①（丢掉 FAT32，改扇区扫描）**，"第几张图在哪个扇区"是**编译时固化在代码里的偏移表**。
用文件管理器拖拽复制会改变扇区排布 → 偏移表全部错位。

```bash
# 主卡验证完成后，先存一份镜像在电脑上
sudo dd if=/dev/sdX of=cpr_final.img bs=4M status=progress

# 现场备用卡启用时，回写（目标卡容量必须 >= 源卡）
sudo dd if=cpr_final.img of=/dev/sdY bs=4M status=progress

# 强烈建议：回读校验，这是比"文件能不能打开"严格得多的自检
sudo dd if=/dev/sdY of=readback.img bs=4M status=progress
cmp cpr_final.img readback.img && echo "镜像一致 ✅"
```

## 6.7 顺带修正：官方"自备设备"那一条，比我们文档写得更严

官方选题一 1.5 原文：

> （1）带有 HDMI 输入显示器，并配备相关数据线。像素建议：**支持基础像素显示 1280×720@60Hz**，推荐使用 **HDMI 1.4 及以上版本的纯铜数据线，长度不超过 5 米**。

两个要注意的点：

1. **官方明文规格是"HDMI 1.4+ 纯铜线、≤5 米、显示器支持 1280×720@60Hz"** —— 我们 `01_竞赛信息/竞赛全流程梳理.md` 的"自备设备（三选一）"漏了这些，应补上。
2. **官方选题一漏写了"带扬声器"**（选题二写的是"带有 HDMI 输入**并带有扬声器或者有音频输出的**显示器"）。
   但选题一**基础要求(4) 明确要求 HDMI 音频输出**，所以**显示器仍必须带喇叭或音频输出**——这一点我们原来的判断是对的。
3. 另外注意：显示器还要能接受 **640×480@60Hz** 输入（本系统输出分辨率）。绝大多数显示器都能，但个别"仅标称 1080p"的低价屏可能拒收。
