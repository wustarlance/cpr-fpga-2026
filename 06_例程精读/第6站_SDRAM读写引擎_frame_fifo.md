**记住这个模型，下面 90% 的代码你都能自己推出来**：

| 模型里的话 | 代码里对应什么 |
|---|---|
| "凑够一车才发" | 写引擎的 `into_burst`：FIFO 里 ≥128 个字才启动突发 |

## 一、它在解决什么问题

### 1.1 问题：两侧的"节奏"完全不匹配

```
bmp_read            frame_fifo_write          SDRAM 控制器        frame_fifo_read      显示
（产出像素）  ──►   （本站）      ──►         （外存）    ──►     （本站）      ──►   （25 MHz 慢慢取）
   不确定              攒批                  要求批量              拆批               稳定节奏
```

三个矛盾同时存在：

| 矛盾 | 具体表现 |
|---|---|
| **速度不匹配** | SD 卡读进来是"一阵一阵"的（0.3~0.5 秒一张图），显示侧却是每帧稳定要 307200 个像素 |
| **粒度不匹配** | FIFO 那头是"一个 32 位像素"，SDRAM 那头**希望一次连续搬一批** |
| **时钟域不匹配** | 写侧跨 100 MHz→125 MHz，读侧跨 125 MHz→25 MHz（第2站的"换乘站"已经解决了跨域，本站只管 FIFO 靠 SDRAM 的那一侧） |

**本站只解决第 2 条：粒度不匹配。** 第 1 条由双缓冲解决（第7站），第 3 条由异步 FIFO 解决（第2站）。

### 1.2 为什么 SDRAM 非要"批量"？——不是设计者偷懒

这是理解本站的**唯一关键**，值得讲透。

SDRAM 内部是一个**二维电容阵列**（行 × 列）。读/写一个数据要经过：

| 步骤 | 干什么 | 相对开销 |
|---|---|---|
| **① 激活（ACTIVATE）** | 把整行的数据**抬到行缓冲器**（sense amplifier）里 | **很大**，几十 ns 量级 |
| **② 列选 + 读写** | 在行缓冲器里按列号取/放数据 | **很小**，一个时钟拍就够 |
| **③ 预充电（PRECHARGE）** | 关掉这一行，准备开下一行 | **很大** |

关键在于：**激活之后，同一行里的数据可以连续快速读写（这叫"页命中"，page hit）**。

所以：

| 做法 | 每 128 个字要付的开销 |
|---|---|
| 一次只读写 1 个字 | 128 次"激活+预充电" |
| **一次连续读写 128 个字** | **1 次"激活"**（地址连续时） |

**结论：批量（burst）不是优化技巧，而是"顺着 SDRAM 的物理特性做事"。** 一次只搬一个字的写法不是"慢一点"，而是**慢几十倍**。

> 📚 **外部参考**：SDRAM 的"激活/读写/预充电"三段式时序、以及"行缓冲器/页命中"的概念，是理解所有 DRAM 的基础。见文末参考 [1][2]。

### 1.3 那为什么突发大小是 128 而不是更大？

因为**候车室只有 512 个座位**（`FIFO_DEPTH = 512`）。突发越大，需要的缓冲越大；缓冲越大，占的 BSRAM 越多（你们方案里的瓶颈资源）。128 是"效率"和"资源"之间的折中。

顺带：`BURST_SIZE` 必须是 **2 的幂**（128 = 2⁷）—— 因为突发地址要求**对齐**（见第七节 7.4）。

## 二、三个数字，把账算清

这三个数字记住，本站的计算题就都会做了：

| 数字 | 出处 | 含义 |
|---|---|---|
| **`BURST_SIZE = 128`** | 两个文件的 `parameter` | 一车 128 个字（1 个"字" = 32 位）|
| **`FIFO_DEPTH = 512`** | 只有**读**引擎有（写引擎不需要，因为写侧用 `rdusedw` 直接看用量） | 候车室 512 个座位 |
| **`FRAME_PIXELS = 307200`** | 顶层 `top_tf_hdmi_audio.v` | 一帧 = 640 × 480 |

### 算一笔账（自己推一遍，以后就不用记了）

```
一帧有多少个字？      640 × 480 = 307200 个字
一车装多少个字？      128 个字
要发多少车？          307200 ÷ 128 = 2400 车        ← 正好整除，没有任何余数
```

**"正好整除"不是巧合，是设计时挑出来的**：如果一帧是 307201 个字，最后一车就只有 1 个字，极端浪费（等于白付一次激活开销）。所以帧长和突发长度都会挑成整除关系。

再算一次**带宽账**：

```
一帧在 125 MHz 域搬完需要多少拍？   307200 拍
                   换算成时间？     307200 ÷ 125e6 ≈ 2.46 ms
显示一帧要多久？                   1 ÷ 60 Hz ≈ 16.7 ms（60 帧/秒）
```

→ **SDRAM 侧只用掉约 15% 的时间预算**，剩下 85% 是空闲的 —— 这就是为什么"再加一路读通道做图层叠加"在带宽上是可行的。但**时序上未必**（见第10节）。

### 3.2 块1：参数与端口

```verilog
parameter MEM_DATA_BITS = 32,      // 一个字 32 位
parameter ADDR_BITS     = 21,      // 地址 21 位 → 最多 2M 个字 = 8 MB（正好是片内 SDRAM 容量）
parameter BURST_BITS    = 9,       // 突发计数器位宽（9 位能数到 512，够数 128）
parameter BURST_SIZE    = 128,     // 一车 128 个字
parameter WRITE_V_FLIP  = 1,       // 写的时候把行序上下翻转（见第六节）
parameter FRAME_WIDTH   = 640,
parameter FRAME_HEIGHT  = 480
```

**先算一次地址空间**，这解释了 `ADDR_BITS = 21` 的来历：

```
2^21 = 2,097,152 个字 × 4 字节/字 = 8,388,608 字节 = 8 MB
```

**正好等于 EG4S20 片内 SDRAM 的容量（2M × 32 位）**。所以 `ADDR_BITS = 21` 不是为了省资源，是**地址空间就这么大**。

端口按"对谁说话"分成三组：

| 组 | 信号 | 对谁 | 备注 |
|---|---|---|---|
| **FIFO 侧** | `rdusedw`（读用量）、`fifo_aclr`（清 FIFO） | 异步 FIFO | 只有"用量"和"清零"两个交互，**没有数据线** |
| **上层请求侧** | `write_req` / `write_req_ack` / `write_finish`、`write_addr_0~3`、`write_addr_index`、`write_len` | 上层状态机 | 请求是**电平**，完成是**脉冲** |
| **SDRAM 侧** | `App_wr_en` / `App_wr_addr`、`Sdr_busy` / `Sdr_init_done`、`App_rd_busy` | SDRAM 控制器 | 见下 |

#### ⭐ 一个关键认识：FIFO 侧**没有数据线**

`rdusedw` 是"FIFO 里现在有多少个字"，模块**只读这个数**；`fifo_aclr` 是"把 FIFO 清空"。

**那数据是怎么从 FIFO 进 SDRAM 的？**

→ **这个模块不搬数据！** 它只产生**地址**（`App_wr_addr`）和**使能**（`App_wr_en`）。数据是 FIFO 直接接到 SDRAM 控制器上的。

```
        ┌──────────── 数据线：FIFO ─────────────► SDRAM 控制器
        │
bmp_read ─► FIFO ─┬─► rdusedw ──► 本站（只出地址和使能）──► SDRAM 控制器的地址口
                  └─► fifo_aclr ◄── 本站
```

**这是一个非常重要、也非常容易看漏的设计**：本站是**控制通路**，不是数据通路。所以它很小（几百行），也不占用大量逻辑资源。

> 📌 **和你们方案的关联**：你们方案里的 `adc_ctrl` / `press_decode` / `rate_judge` 也是同样的角色 —— **只出控制信号，数据自己走**。这种"控制与数据分离"是硬件设计的通用套路（第4站 `bmp_read` 里也是主状态机只管流程、数据通路独立）。

#### 术语卡（块1）

| 术语 | 意思 |
|---|---|
| **`App_*`** | "Application port" 的缩写，指 SDRAM 控制器**给用户侧**的接口（用户不用管刷新、时序，只管要地址） |
| **`usedw`** | used words，"已用量"。FIFO 的标准状态输出，读侧看 `rdusedw`、写侧看 `wrusedw` |
| **`fifo_aclr`** | asynchronous clear，异步清零。这里用于"开始新一帧时把上一帧残留清掉" |
| **`Sdr_busy`** | SDRAM 自己在忙（刷新、其他 bank 操作），此时不能发请求 |

### 3.3 块2：常量与状态码

```verilog
// 行序翻转的三个常量（推导见第六节）
localparam VFLIP_FIRST_ADDR_OFFSET = (FRAME_HEIGHT - 1) * FRAME_WIDTH;  // 479 × 640 = 306560
localparam VFLIP_LINE_JUMP         = (FRAME_WIDTH * 2) - 1;             // 1280 - 1  = 1279
localparam VFLIP_LINE_LAST_X       = FRAME_WIDTH - 1;                   // 639

// 6 个状态
localparam S_IDLE            = 0;  // 空闲，等请求
localparam S_ACK             = 1;  // 应答 + 清 FIFO + 锁存地址/长度
localparam S_CHECK_FIFO      = 2;  // 检查 FIFO 够不够一次突发
localparam S_WRITE_BURST     = 3;  // 正在发突发
localparam S_WRITE_BURST_END = 4;  // 一次突发结束，判断整帧完没完
localparam S_END             = 5;  // 整帧完成
```

**注意状态码从 0 到 5 连续**，而第5站的 `sd_card_cmd.v` 是 0~8 然后跳到 14~17（当时标记为"坏味道"）。**同一个人写的两个文件风格不一致** —— 这是"坏味道"里值得注意的一类：**跳号只说明改过，不说明对错**。

### 3.4 块3：跨时钟域同步

```verilog
write_req_d0 <= write_req;      // 第1拍
write_req_d1 <= write_req_d0;   // 第2拍
write_req_d2 <= write_req_d1;   // 第3拍  ← 注释原文：Why do you need 3 ? Here's the design habit
```

**这三行在干什么？为什么不能直接用 `write_req`？**

因为 `write_req` 来自**别的时钟域**（上层的 SD/显示域），而本站工作在 `mem_clk`（125 MHz）。**直接采一个异步信号会产生亚稳态**（信号恰好在这拍的建立/保持窗口里跳变，触发器可能输出一个既非 0 也非 1 的中间电平，还会传播下去）。

**两级触发器是标准解法**：

| 级 | 作用 |
|---|---|
| 第 1 级 | 可能输出亚稳态，但**给它一整拍时间去稳定** |
| 第 2 级 | 采到的是"已经稳定的上一拍值" |
| 第 3 级 | **没有额外作用**，只增加一拍延迟 |

> 📚 **外部参考**：两级同步器是 CDC（跨时钟域）的标准做法，因为第二级在下一拍采样时第一级已经稳定，MTBF（平均无故障时间）已经足够高；再加级数只提升 MTBF，不改变功能。见文末参考 [3][4]。

**但这里有个真问题**（详见第八节坏味道）：**`write_req` 打了 3 拍，`write_len` 只打了 2 拍**。也就是说，当状态机看到 `write_req_d2` 时，`write_len_d1` 已经是**更晚一拍**采样的值。**两者不同步**。

为什么这里没出错？因为 `write_len` 在整个请求期间是稳定的（顶层给的是常数 `FRAME_PIXELS`），晚采一拍也一样。**这叫"靠巧合正确"** —— 只要有人改了上层让 `write_len` 变成动态值，这里就会出错。

### 3.5 块4：地址生成与行序翻转（本站最绕的一块）

```verilog
if(state == S_ACK)
    App_wr_addr_r <= WRITE_V_FLIP ? (write_addr_N + VFLIP_FIRST_ADDR_OFFSET) : write_addr_N;
else if(App_wr_en)
    if(WRITE_V_FLIP)
        if(wr_x == VFLIP_LINE_LAST_X) begin              // 写到行尾了
            wr_x <= 0;
            App_wr_addr_r <= App_wr_addr_r - VFLIP_LINE_JUMP;   // ★ 往回跳一行
        end else begin
            wr_x <= wr_x + 1; App_wr_addr_r <= App_wr_addr_r + 1;
        end
    else
        App_wr_addr_r <= App_wr_addr_r + 1;              // 不翻转：就是简单递增
```

**分三种时机看地址怎么变**：

| 时机 | 动作 | 效果 |
|---|---|---|
| **开始一帧**（`S_ACK`） | 基地址 + 306560 | 直接落到**第 479 行**（最后一行） |
| **行内每写一个字** | +1 | 往右走一格 |
| **写到行尾**（`wr_x == 639`） | −1279 | 往上一行，回到行首 |

`wr_x` 就是"这一行写到第几个像素了"，数到 639 就换行。

**为什么行尾是 −1279 而不是 −640？** 见第六节 —— 那是一笔需要算清楚的账。

**读引擎没有这一段**（读侧只有 `App_rd_addr_r <= App_rd_addr_r + 1`）。原因很简单：**写侧已经翻过了，读出来就是正的**（第2站那句"在写入时翻转，读侧就不用管了"就是说的这里）。

### 3.6 块5：状态机

```
                    ┌──────────────────────────────────────────┐
                    ▼                                          │
  复位 ──► S_IDLE ──► S_ACK ──► S_CHECK_FIFO ──► S_WRITE_BURST ──► S_WRITE_BURST_END
             ▲          ▲            │                                   │
             │          │            │ 上层又来请求(换帧)                  │ write_cnt >= write_len
             │          └────────────┴───────────────────────────────────┤
             │                                                           ▼
             └──────────────────────────────────────────────────────  S_END
                              S_END 高 1 拍 = write_finish
```

| 状态 | 进入条件 | 干什么 | 离开条件 |
|---|---|---|---|
| `S_IDLE` | 复位 | 等 `write_req_d2 && Sdr_init_done` | 条件满足 → `S_ACK` |
| `S_ACK` | 收到请求 | ① 回应答 ② 清 FIFO ③ 锁地址 ④ 锁长度 | 上层撤销请求（`write_req_d2 == 0`）→ `S_CHECK_FIFO` |
| `S_CHECK_FIFO` | 请求已撤销 | 判断"能不能发车"（见第四节） | 能发 → `S_WRITE_BURST`；上层又来请求 → `S_ACK` |
| `S_WRITE_BURST` | — | 连续拉高 `App_wr_en` 共 128 拍 | 数到 128 → `S_WRITE_BURST_END` |
| `S_WRITE_BURST_END` | — | 累加 `write_cnt += 128` | 没写完 → `S_CHECK_FIFO`；写完 → `S_END`；上层又来 → `S_ACK` |
| `S_END` | 整帧写完 | `write_finish` 高 1 拍 | → `S_IDLE` |

#### ⭐ 一个容易看漏的设计：为什么 `S_ACK` 之后就"撤销请求"了？

```verilog
S_ACK: if(write_req_d2 == 1'b0) begin state <= S_CHECK_FIFO; ... end
```

**它要求上层在收到应答后把请求拉低**。注释原文（第31行端口处）写着：

> `keep '1' until write_req_ack = '1'`

这是**标准的两拍请求握手**（req → ack → 撤销 req），和本站开头说的"请求电平、完成脉冲"是同一套规则，第1站的 `read_req`、第5站的 `sd_sec_read` 都是这个模式。

> 📚 **外部参考**：`req/ack`（也叫 2-way / 4-way handshake）和 AXI 的 `valid/ready` 是两种常见握手风格。简单低速的模块间通信用手写的 req/ack 就够；总线互连上则用 valid/ready（因为它更容易组合与流水）。本站属于前者。见文末参考 [5]。

#### 术语卡（块3~5）

| 术语 | 意思 |
|---|---|
| **亚稳态（metastability）** | 触发器在建立/保持窗口内采样到跳变信号时，输出可能悬在中间电平并传播 |
| **两级同步器** | 第一级可能亚稳，第二级采到已稳定值；是 CDC 的标准最小配置 |
| **突发（burst）** | 一次连续读写一批数据，中间不重新激活行 |
| **流控（flow control）** | 靠 FIFO 用量决定"现在能不能搬"，防止溢出/读空 |
| **水位 / 阈值（watermark）** | 触发动作的用量门限，如这里的 128 和 384 |

## 四、核心分析①：流控的两条判据

### 4.1 写引擎：什么时候能"发车"

```verilog
assign into_burst = (((write_len_latch <= (rdusedw + write_cnt)) || rdusedw > BURST_SIZE)
                     && ~App_rd_busy);
```

拆成三个条件，**从"公交模型"理解**：

| 条件 | 含义 | 用候车室的话说 |
|---|---|---|
| `rdusedw > BURST_SIZE` | FIFO 里超过 128 个字 | **"人挤到超过一车了，赶紧拉走一车"** |
| `write_len_latch <= (rdusedw + write_cnt)` | 剩余的 + 已搬的 ≥ 一帧总量 | **"这是最后一车了，别等凑满，有多少拉多少"** |
| `~App_rd_busy` | 读引擎不在忙 | **"门口只有一条道，对面车在用就等等"** |

### 4.2 读引擎：什么时候能"进货"

```verilog
else if(wrusedw < (FIFO_DEPTH - BURST_SIZE) && ~App_wr_busy)
```

| 条件 | 含义 | 算一下 |
|---|---|---|
| `wrusedw < (FIFO_DEPTH - BURST_SIZE)` | 候车室至少空得下一车 | `512 - 128 = 384`，即"已写入量 < 384" |
| `~App_wr_busy` | 写引擎不在忙 | 同上，互相避让 |

### 4.3 ⭐ 为什么阈值是 128 / 384，而不是"满/空"？

这是本站最值得学的一个思维点。

**不能用"空/满"当阈值，因为状态变化需要时间**：

```
读引擎判断"FIFO 还有空间" ──► 发出突发读 ──► 数据回来需要若干拍
                                                    ↓
                                        这几拍里写引擎可能又塞进新数据
```

如果等到 `wrusedw` 快到 512 才动手，在"判断→数据真正写进 FIFO"的这段延迟里，写侧可能已经把 FIFO 塞满 → **溢出，数据丢失**。

**所以工程上总是留一个"安全余量"（水位）**：

| 判据 | 余量 |
|---|---|
| 读侧要"至少空一个突发" | 预留 128 |
| 写侧要"至少有一个突发"才动手 | 预留 128 |

> 📚 **外部参考**：这正是 FPGA FIFO IP 里"**可编程满/空（prog_full / prog_empty）**"存在的理由 —— 它让你设置一个**提前于**真正满/空的水位，用它做流控才能抵消内部延迟。见文末参考 [6][7]。

**这也解释了为什么 `FIFO_DEPTH` 必须大于 `BURST_SIZE` 的两倍左右**：候车室得同时容纳"正在被搬走的一车"和"正在进站的一车"，否则永远凑不满。

### 4.4 ⭐ 那个"逃生分支"解决的边界问题

`write_len_latch <= (rdusedw + write_cnt)` 这一项看着多余，其实**必不可少**。

**问题**：一帧 307200 个字 = 2400 车，正好整除。但**万一不整除呢**？

假设一帧 307300 个字（假想）：搬完 2400 车（307200）后剩 **100 个字**。

| 没有逃生分支 | 有逃生分支 |
|---|---|
| 判据 `rdusedw > 128` 永远不成立（只剩 100 个） | 判据 `write_len(307300) <= rdusedw + write_cnt(307200)` 成立 |
| **死等，整帧永远写不完** | 把剩下 100 个也发出去，正常结束 |

**这是一类通用陷阱**：凡是用"阈值 + 计数"的地方，都要问一句"**最后一批不满阈值怎么办？**"。

> 你们方案里 `rate_judge` 用"相邻间隔区间判定"、`peak_detect` 用双门限，都会遇到同类问题（最后一拍数据不足时怎么办）。**这条经验可以直接搬过去。**

## 五、核心分析②：★ 兑现第3站的悬念

### 5.1 悬念回顾

第3站讲过：**消隐期不读 FIFO，能省约 27% 读带宽**。

```
不省的时候：按 800 × 525 读  = 420,000 次
省的时候：  按 640 × 480 读  = 307,200 次
省下来：    (420000 - 307200) / 420000 = 26.86% ≈ 27%     ← 27% 是这么来的
```

当时留了一个条件：**"前提是写端也只写有效像素"**。
如果写端把消隐期也算进去写了 420000 个，那缓存里就混着无效数据，读端想跳过也跳不掉。

### 5.2 答案：成立，而且比想象的更简单

**证据一：写引擎根本没有 `de` 端口。**

翻遍端口表，没有任何"这一拍是有效像素"的输入。它只认一个数：`write_len`。

**证据二：顶层给的 `write_len` 就是有效像素数。**

```verilog
// top_tf_hdmi_audio.v
parameter FRAME_PIXELS = 24'd307200;   // 640*480
...
.write_len  (FRAME_PIXELS),            // 第 269 行
.read_len   (FRAME_PIXELS),            // 第 251 行
```

写引擎数到 `write_cnt < write_len_latch` 就停 —— **正好 307200 个字，一个不多**。

**证据三（关键）：写引擎的上游 `bmp_read` 压根不知道"消隐期"是什么。**

`bmp_read` 读的是 **BMP 文件**。BMP 文件里没有消隐期 —— 它只有 640 × 480 个像素。

### 5.3 所以结论是

| 问题 | 答案 |
|---|---|
| 帧缓存里装的是什么？ | **只有 307200 个有效像素**，从来没有消隐期数据 |
| 读端凭什么能省 27%？ | 因为缓存里本来就只有有效像素，消隐期**无事可做** |
| 那个"前提"成立吗？ | ✅ 成立，而且**不是靠门控，是结构上就写不进去** |

> **一句话**：这个设计里"**显示分辨率**"和"**存储分辨率**"是同一个 640×480。消隐期只存在于**显示时序**里，从来不进存储器。这就是 27% 省下来的根本原因。
>
> **给你们的推论**：只要你们也只把有效像素写进帧缓存，读侧的 27% 就自动省下来，**不需要任何额外逻辑**。反过来说，**如果哪天你们为了省事把整行 800 像素都写进缓存（比如让 `layer_mixer` 在消隐期也输出数据），这 27% 立刻消失** —— 这是一个容易被顺手破坏的性质，要写进你们的规范。

## 六、核心分析③：行序翻转那笔账

### 6.1 为什么需要翻转

第4站讲过：**BMP 的行序是"从下到上"**（高度为正时）——文件里第一个像素是图像的**左下角**。

而显示是**从上到下**扫描的。所以必须翻一次。**在哪翻？** 两个选择：

| 方案 | 做法 | 代价 |
|---|---|---|
| 在 `bmp_read` 里翻 | 解析时把行倒着输出 | 要缓存一整行（640 个像素）才能倒序 |
| **在本模块翻**（实际选择） | **数据流顺序不变，只把写入地址倒过来** | **零额外缓存** |

**这是"用地址做变换"的经典手法** —— 不动数据，只动地址。第3站的 `video_delay` 是"用延迟做变换"，这里是"用地址做变换"，思路同类。

### 6.2 推导三个常量

**目标**：数据流第 0 行 → 存到第 479 行；第 1 行 → 存到第 478 行；……

**① 起始偏移**（`VFLIP_FIRST_ADDR_OFFSET`）

```verilog
(FRAME_HEIGHT - 1) * FRAME_WIDTH = 479 × 640 = 306,560
```

第 479 行的起始地址就是 `479 × 640`。所以一帧开始时，**直接把地址设到 306560**，从最后一行开始写。

**② 行尾常量**（`VFLIP_LINE_LAST_X`）

```verilog
FRAME_WIDTH - 1 = 639
```

`wr_x` 从 0 数到 639，共 640 个像素 = 一行。

**③ 行跳常量**（`VFLIP_LINE_JUMP`）—— 这笔账要算清

在 `wr_x == 639` 那一拍，**地址已经加到了哪里**？我们跟着走一遍：

| 时刻 | `wr_x` | 本次写的地址 | 写完后的 `App_wr_addr_r` |
|---|---|---|---|
| 写行首（第 0 个像素） | 0 | A | A+1 |
| 写第 1 个像素 | 1 | A+1 | A+2 |
| … | … | … | … |
| 写第 639 个（行尾） | 639 | **A+639** | 需要跳到"上一行的行首" |

**注意：条件判断发生在"写这一拍"，此时用的地址是 `App_wr_addr_r` 的当前值（= A+639），而赋值是给下一拍用的。**

要去的目标地址 = **上一行的行首** = `(A - 640) + 1 = A - 639`

（为什么是 `A-640+1`？因为 `A` 是第 479 行的行首，上一行（第 478 行）的行首是 `A - 640`；而我们希望**下一拍从上一行的第 1 个像素开始**，所以还要 +1。第 478 行行首那一格已经在本行的上一次"行尾跳转"时用过了 —— 这是个容易绕晕的地方，见下。）

于是：

```
下一拍地址 = (A - 639)
当前地址   = (A + 639)
差值       = (A + 639) - (A - 639) = 1278
```

所以 `App_wr_addr_r <= App_wr_addr_r - 1278`？

**可是代码写的是 −1279。差 1，为什么？**

因为**条件判断用的是"当前拍还没写的那个地址"**。精确地重数一遍，注意 `App_wr_addr_r` 的更新时机：

| 拍 | `App_wr_en` | `wr_x`（当前值） | `App_wr_addr_r`（当前值） | 本拍用哪个地址写 |
|---|---|---|---|---|
| 0 | 1 | 0 | A | **A** |
| 1 | 1 | 1 | A+1 | **A+1** |
| … | | | | |
| 639 | 1 | 639 | A+639 | **A+639** |
| 640 | 1 | 0 | 目标 | **目标** |

在拍 639 时，`App_wr_addr_r = A + 639`，而**目标（拍 640 要用的地址）**是上一行的行首 `A - 640`。

```
A - 640 = (A + 639) - 1279
        = 当前值 - 1279                       ✅ 与代码一致
```

**所以 −1279 = −640（退一行）− 639（把已经走过的 639 格补回来）。**

> ⭐ **这个推导比结论重要**：凡是"地址跳变"类的代码，**不能只看表达式，必须把"判断发生在哪一拍、赋值给哪一拍用"数清楚**。差 1 的错误在这类代码里极常见，而且仿真时看着"差不多能用"（图像错半个像素），很难查。

### 6.3 算一下翻转会不会破坏突发对齐

第 7 节 7.4 会讲突发地址要对齐。先算：

```
起始地址  306560 ÷ 128 = 2395.0    → 整除 ✅
缓冲区基址 307200 ÷ 128 = 2400.0    → 整除 ✅
```

**起始地址是对齐的**，好。但**行尾跳转会发生在任意位置**，也就是说：

> ⚠️ **一次突发（128 拍）可能"跨行"** —— 突发的前半段在行 479 的尾部，后半段跳到行 478 的开头。**这个突发内部的地址不连续。**

**这会怎样？** 取决于 SDRAM 控制器（`sdr_as_ram`）怎么处理：它是每拍取一个新地址（那么跨行只是多一次行激活，效率略降），还是假设 128 个地址连续（那就会出错）。

**本站无法回答** —— 需要看 `sdram.v` / `sdr_as_ram`（未走读）。**已记为待确认项**（见第10节）。

## 七、几个额外的细节

### 7.1 `rd_delay`：读引擎里那个"等 10 拍"

```verilog
assign rd_vld = (state == S_READ_BURST && burst_cnt >= BURST_SIZE);
assign rd_burst_finish = (rd_vld && rd_delay == 4'd10);
```

读引擎不像写引擎那样"发完 128 个就算完"。它数到 128 个**读地址发完**后，还要**再等 10 拍**才认为数据真的到齐了。

**为什么？** 注释原文解释得很清楚（而且是原作者自己写的中文）：

> `//burst_cnt代表发送的读指令`
> `//但rd_burst_finish需要在发送完十个时钟后拉高，此时数据全部读出`

**这是"发出请求"和"拿到数据"之间的固有延迟**（SDRAM 的读延迟 CAS latency）。写方向不存在这个问题（写完就完事），读方向必须等。

**这就是第3站"读延迟补偿"的同一个道理**：**请求发出的时刻 ≠ 数据可用的时刻**。第3站用 `video_delay` 在系统层面补，这里在引擎内部补。

> 那个 `10` 是个**魔数**，硬编码在代码里。它必须 ≥ SDRAM 的读延迟。**如果换了 SDRAM 参数或时钟比，这个 10 就要重算** —— 属于"改环境就会坏"的地方。

### 7.2 "每拍给地址"的接口形式 —— 为什么翻转能在这里做

```verilog
assign App_wr_addr = App_wr_addr_r;    // 组合输出，每拍都能变
```

**这个模块每拍都给一个新地址**（不是"给一个基地址 + 长度，让控制器自己递增"）。正因为地址是**逐拍生成**的，行序翻转才能在这里实现（翻转本质就是"逐拍改地址"）。

如果接口是"基地址 + 突发长度"那种（被注释掉的那套 `wr_burst_addr/wr_burst_len`），翻转就必须放到控制器里做，或者先翻转数据流。**接口形式决定了功能能放在哪一层** —— 这是接口设计的一个好例子。

### 7.3 `Sdr_init_done` / `Sdr_busy` 的作用

| 信号 | 用在哪 | 不用会怎样 |
|---|---|---|
| `Sdr_init_done` | `S_IDLE` 的进入条件 | SDRAM 初始化没完成就发请求 → 请求丢失或数据错乱 |
| `Sdr_busy` | 端口引出，但**本模块内部似乎没用到** | ⚠️ 见第八节 |
| `App_rd_busy` / `App_wr_busy` | 互相避让 | 两个引擎同时发请求 → 冲突 |

### 7.4 顺带补一个通用知识：突发地址要对齐

DRAM 的突发访问要求**起始地址按突发长度对齐**（128 个字 → 地址低 7 位为 0）。

| 平台 | 对齐要求 |
|---|---|
| 通用 DRAM | 起始地址 = 突发长度 × 整数 |
| AXI 总线（ARM） | 突发**不能跨越 4 KB 边界**（4 KB 正好是很多存储系统的一页） |

见文末参考 [8][9]。

**这解释了为什么 `BURST_SIZE` 是 2 的幂**：只有 2 的幂才能用"地址低位清零"这种便宜的方式判断/生成对齐地址。**这不是随意挑的数，是被硬件约束逼出来的。**

## 八、一个"坏味道"（其实是三个）

### 8.1 同步级数不一致（**真问题**）

```verilog
write_req_d0/d1/d2   ← 3 拍
write_len_d0/d1      ← 2 拍
write_addr_index_d0/d1 ← 2 拍
```

**三个本该同步的信号用了不同的级数**，导致状态机看到 `write_req_d2` 时，采到的 `write_len_d1` 是**晚一拍的样本**。

- 现在没坏，因为 `write_len` 是常数；
- 但这是**"靠巧合正确"**，属于最容易在后续修改中被踩的类型；
- 原作者自己在注释里都写了 `Why do you need 3 ? Here's the design habit` —— **他知道多余，但没统一**。

**正确做法**：三个信号**同一级数（2 级）**，并且**同时刻采样**。

### 8.2 大段注释掉的死代码

两个文件各有一大段 `/* */` 包起来的旧接口：

```verilog
/*
output reg [BURST_BITS-1:0] wr_burst_len,   // 突发长度
output reg [ADDR_BITS-1:0]  wr_burst_addr,  // 突发基地址
input                       wr_burst_data_req,
input                       wr_burst_finish,
*/
```

说明**原作者重构过**：早期是"基地址 + 长度"的突发接口，后来改成"逐拍给地址"（见 7.2）。

**读的时候直接跳过**，但要知道：**这些死代码解释了"为什么这段代码有点绕"**。它们还占着几百字节，清掉能减少阅读负担。

### 8.3 `ONE` / `ZERO` 的炫技写法

```verilog
localparam ONE  = 256'd1;    // 注释：you can use ONE[n-1:0] for n bit '1'
localparam ZERO = 256'd0;
...
write_len_d0 <= ZERO[ADDR_BITS - 1:0];    // 等价于 write_len_d0 <= 0;
```

**用 256 位常量切片来表示 0** —— 功能等价，但**读起来要绕一层**。注释自己都写了 "equivalent to 0"。属于**为了"优雅"牺牲可读性**的典型，不建议学。

（顺带：`Sdr_busy` 引出了端口但模块内部没用到 —— 可能是给别的版本留的。**这类"引而未用"的信号会让读者怀疑自己看漏了**，属于接口卫生问题。）

## 十一、检查题
