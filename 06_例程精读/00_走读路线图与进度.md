### 三条硬规矩

1. **末尾三节固定**：`能学到什么` → `你们的实现会不会用这个电路？` → `检查题`。
   第1站的"⚠️ 文件被改过的地方"、第2站的"两个额外的细节"、第3站的"三个额外的细节 + 坏味道"——**这些特殊内容一律放在「能学到什么」之前**。
   （第3站初稿把"坏味道"和"[31:8]"插在了「会不会用」和「检查题」中间，已修正。）

2. **每块代码后面给术语卡**：用表格，一行一个术语。三个人的基础不一样，术语解释不能省。

3. **⭐ 不要为了"短"而压缩 —— 要为了"有逻辑"而展开。**（2026-09-20 用户反馈）
   > 原话："代码太多了我记不过来，**你说的越详细越有逻辑，我能记住的东西反而越多**。你也可以结合网上的教程来教我，可以多上网。"

   **核心认识**：读者的困难不是"文字太长"，而是"**代码太多、没有抓手**"。所以解法不是少讲，而是**给一副能挂住所有细节的骨架**。具体做法：

   | # | 做法 | 为什么有效 |
   |---|---|---|
   | 1 | 每站开头先给**一句话心智模型**（最好带类比），全站内容都往它上面挂 | 记住一个模型 = 记住了全站 |
   | 2 | 讲代码**前**先讲"它要解决什么问题"；讲完代码再回头对一遍 | 建立"问题→方案"的因果，而不是背代码 |
   | 3 | 关键数字**算给读者看**（如 307200 ÷ 128 = 2400），不要只报结论 | 自己推过一遍就不会忘 |
   | 4 | 主动**横向连接**：和前面某站、和其他领域的同类做法对照（AXI burst / ready-valid / prog_full / CDC） | 一个概念在多个地方出现 = 真正学会 |
   | 5 | **可以多上网**找权威资料佐证，并在文末列出链接 | 有出处的结论才敢信、才记得住 |
   | 6 | 难度分层：`★` 必懂 / `☆` 选读 / 明确标"本站不讲" | 知道哪里可以暂时放过，才不至于被淹 |

   **反面例子**：第6站初稿（259 行）为了"写短"把推导、类比、外部对照全砍了 —— 已按本规则重写为详版。

### 每个模块都必须回答的两个问题

- **你们的实现会不会用这个电路**：会 / 不会 / 部分，以及**建议怎么改写**（不是照抄）

## 关键结论速查（走读过程中攒下来的）

| 结论 | 出处 |
|---|---|
| **FIFO 的 `clkw` 跟"数据从哪来"，`clkr` 跟"数据到哪去"** | 第2站 |
| `rfifo_32_32_512 read_buf` 的 `clkw` 才是 `mem_clk` | 第2站 Q1 |
| `frame_read_write.v` 有 **0 个 `always` 块**（纯结构化模块） | 第2站 Q2 |
| 改三缓冲**不用动** `frame_read_write.v`——它已预留 **4 组地址 + 2 位索引** | 第2站 Q3 |
| `read_en` 的读延迟是 **1 拍**（注释原文 "read_data valid next clock"） | 第2站 |
| `read_en` 比 `de_r` 早 **2 拍** = FIFO 1 拍 + 输出寄存器 1 拍 | 第3站 |
| 消隐期不读 FIFO，**省约 27% 读带宽** | 第3站 |
| 数据通路是 **32 位存储 → 取 `[31:8]` → 24 位显示**（RGB888） | 第3站 + 顶层 |
| SDRAM 地址单位是**"32位字"**，不是字节（`BUF1_ADDR=307200`=640×480） | 第2站 |
| `startup_pulse` 的延时 = 100000 ÷ 25MHz = **4ms** | 第0站 |
| 读写仲裁规则：**写优先**（数据丢了找不回来的一方优先） | 第2站 |
