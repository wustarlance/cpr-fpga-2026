## 第4站：`bmp_read.v` —— BMP 文件解析

| 项 | 内容 |
|---|---|
| 文件 | `SD/bmp_read.v`（约 300 行，11.3 KB） |
| 在链路里的位置 | SD 卡 → **BMP 解析** → 帧缓存写入 |
| 干什么 | 把 SD 卡上读到的原始字节流，解析成"一行一行的 RGB 像素" |

### 读之前先搞懂：BMP 文件格式

BMP 是最简单的图片格式——**没有压缩**，所以最适合 FPGA 解析。三个关键点：

| 字段 | 位置 | 为什么重要 |
|---|---|---|
| **文件头 magic `"BM"`** | 偏移 0~1 | 判断这是不是 BMP |
| **像素数据起始偏移** | 偏移 10（4 字节） | 从文件第几个字节开始才是像素 |
| **宽、高** | 偏移 18、22（各 4 字节） | 算出每行多少像素、总共多少行 |
| **每行字节数** | 由宽度算出，且**必须 4 字节对齐** | **最容易踩的坑**：宽 640 × 3 字节 = 1920，能整除 4 所以没事；但宽 641 就要补填充字节 |

> ⚠️ **BMP 的行序是"从下到上"**（高度为正时）。
> 这就是第2站 `WRITE_V_FLIP = 1` 存在的原因——**在写入时翻转，读侧就不用管了。**

### 带着这些问题去读

1. 它怎么支持**多种分辨率**的 BMP？（`FRAME_WIDTH/HEIGHT` 是参数，还是从文件头读出来的？）
2. **4 字节对齐的填充**在哪里被跳过？
3. 像素顺序是 BGR 还是 RGB？如果是 BGR，在哪里换的？
4. 它一次从 SD 卡要多少个字节？（这决定了时序和 FIFO 深度）

### 能学到什么

- **文件格式解析的一般套路**：找 magic → 定位头部字段 → 跳过不关心的部分 → 提取有效载荷
- **字节序（endianness）**：BMP 是小端（低位字节在前），FPGA 里拼字节要特别注意

## 第5站：SD 卡 SPI 链路

| 项 | 内容 |
|---|---|
| 文件 | `sd_card_top.v`（7.3KB）/ `sd_card_bmp.v`（15KB）/ `sd_card_cmd.v`（8.6KB）/ `sd_card_sec_read_write.v`（5.6KB）/ `spi_master.v`（3.7KB） |
| 在链路里的位置 | **整条链路的起点** |
| 干什么 | 通过 SPI 协议读 SD 卡上的扇区，并从中取出 BMP 文件的字节 |

### 分层关系（先理解这个，再看代码）

```
sd_card_top.v          ← 最上层：读文件？读扇区？对外给接口
      │
sd_card_cmd.v          ← SD 卡命令层（CMD0/CMD8/CMD17/CMD24...）
      │
sd_card_sec_read_write.v ← 扇区读写（512 字节一次）
      │
spi_master.v           ← 最底层：SPI 时序（时钟、MOSI/MISO、片选）
```

**术语**：**分层**——每一层只跟相邻层打交道，底层只管"怎么把字节发出去"，上层只管"发什么字节"。

### 读之前先搞懂：SD 卡的两个基础概念

| 概念 | 意思 |
|---|---|
| **扇区（sector）** | SD 卡的最小读写单位，**固定 512 字节**。不能只读 1 个字节 |
| **CMD17 / CMD24** | 单块读 / 单块写命令。SD 卡的读写全靠发命令 |

> **SD 卡初始化很讲究**：上电后要先发 CMD0（复位）、CMD8（查电压）、ACMD41（问 OCR，等卡就绪）……**顺序错了卡就不响应**。这是调试时最常见的坑。

### 带着这些问题去读

1. 初始化状态机有几个状态？卡就绪（`ready`）信号是怎么产生的？
2. **一次读一扇区要多少拍？** （决定读一张 640×480×3 字节的图要多久）
3. 有没有做**超时保护**？卡拔掉了会怎样？
4. **这个工程用 FAT32 文件系统吗？还是直接按扇区地址读？** ← 这个问题的答案很关键

> 💡 **第 4 问很可能是"直接按扇区读"**。因为简单工程常常把 BMP **从扇区 0 开始裸放**，跳过文件系统。如果真是这样，**你们就要决定**：是照做（简单，但换图要从特定扇区烧写），还是自己写 FAT32（复杂，但能直接放文件）。

### 能学到什么

- **SPI 主机（master）的通用写法**（时钟分频、相位极性、片选）
- **命令-响应协议**（发命令 → 等响应 → 收数据），和第1站的 `req/ack` 是同一类思想
- **状态机的写法**：一个状态一件事，`case` 分支清晰列出

## 第6站：`frame_fifo_write.v` / `frame_fifo_read.v` —— SDRAM 读写引擎

| 项 | 内容 |
|---|---|
| 文件 | `frame_fifo_write.v`（11.5KB）/ `frame_fifo_read.v`（10KB） |
| 在链路里的位置 | 夹在异步 FIFO 和 SDRAM 控制器之间 |
| 干什么 | 把 FIFO 里的零散数据，组织成 **burst（突发）** 交给 SDRAM；反过来也一样 |

### 读之前先搞懂：为什么要 burst

SDRAM 每次"行激活"开销很大，所以**一次连续读写一批**（叫突发）比一次读一个字节高效得多。

| 术语 | 意思 |
|---|---|
| **burst（突发）** | 一次连续读写 N 个数据 |
| **BURST_SIZE = 256** | 本工程一次突发 256 个字 = **1KB** |
| **Sdr_busy** | SDRAM 正忙（刷新/其他操作），要等 |

### 这一站兑现第3站留下的那个悬念

第3站说：**"消隐期不读 FIFO 能省 27% 带宽，前提是写端也只写有效像素"**。
→ **答案就在 `frame_fifo_write.v` 里**：看它有没有用 `de` 来门控写使能，以及 `write_len` 是怎么数的。

### 带着这些问题去读

1. 写引擎怎么知道"一帧写完了"？（数到 `write_len` 就停？）
2. 一帧 307200 个像素、每次突发 256 个 → 要发多少次突发？
3. **写端是按有效像素计数，还是按 800×525 计数？**（直接决定第3站那个 27% 成不成立）
4. 读写冲突怎么处理？（回到第2站看到的"写优先"）
5. `Sdr_init_done` / `Sdr_init_ref_vld` 是怎么用的？没初始化完会怎样？

### 能学到什么

- **突发接口的状态机**（IDLE → 发请求 → 等 busy → 送数据 → 完成）
- **地址递增与边界判断**（写满一帧自动停止）
- **流控（flow control）**：`rdusedw` / `wrusedw` 用量计数怎么用来防止 FIFO 溢出/读空

```

⑦ 音频通道           → hdmi_audio_tone_i2s_64fs → I2S_receiver → audio_arc_calculate
⑧ 双缓冲切换         → write_buf_idx / disp_buf_idx 谁在改？
```

### 顺便核对三张表（我们在前几站已经算出来了，用顶层验证）

### 带着这些问题去读

1. **`write_buf_idx` 和 `disp_buf_idx` 分别在哪里被改？** 改的时机对不对（会不会读到正在写的那一块）？

### 能学到什么
