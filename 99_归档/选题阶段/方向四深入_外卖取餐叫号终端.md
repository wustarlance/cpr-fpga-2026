# 方向四深入：外卖取餐叫号显示终端

> 本文回答两个关键疑问，并把"门店叫号"深化为**外卖取餐点叫号**——一个有真实数据支撑、且能解决"动态数据从哪来"的场景。

---

## 一、疑问一：现实中会用 SD 卡吗？

### 诚实回答：真实商显基本不用 SD 卡，用网络下发

所以如果作品一路宣传"换 SD 卡换内容"，一定会被问："**为什么不用网络？**"

### 但更严重的问题是你戳到的这个：**叫号是动态数据，SD 卡根本提供不了**

订单号每几分钟就变一次，存不进卡里。**原方向四在这里是自相矛盾的。**

### 正确的分工

| 数据 | 性质 | 更新频率 | 来源 |
|---|---|---|---|
| 菜单图、优惠文案、品牌画面、背景音乐 | **静态素材** | 几天/几周一次 | **SD 卡**（合理） |
| 订单号、出餐状态 | **动态数据** | 随时在变 | **本地接口（串口）** |

**两条依据让 SD 卡站得住**：

1. **赛题 1.3 原文就要求**：「本地图像资源扫描、BMP 图像解析、SDRAM 帧缓存管理」——**本地存储是题目设定，不是我们的选择**
2. **两路数据汇入 FPGA 实时融合成一幅画面**——这正好是赛题原话里的「**多源信息融合**」

> **换句话说：你的疑问，恰好把作品从"播放器"升级成了"多源信息融合终端"。**

## 二、疑问二：实用性高不高？

### 场景的真实数据

**规模**（新浪新闻转九派新闻，2026-05-30）：

- 全国即时配送骑手已接近 **2000 万人**
- 支撑**日均约 1.1 亿订单**
- 2025 年 2 月起，京东、淘宝闪购与美团三方累计烧掉**千亿补贴**；大战期间新增骑手超 800 万人

**痛点**（蜀山新闻网，2026-09-14，就在上周）：

> 「每到午餐、晚餐高峰时段，**数百名外卖骑手同时在商场内穿行取餐**，奔跑赶单，与商户和保安人员之间的摩擦不断累积。**出餐速度与等待预期之间的"时间差"，也常常点燃火药桶。**」
> 「矛盾纠纷警情时有发生，警力被大量牵制」「商场外骑手电动车随意停放、占道等单，周边道路拥堵不堪，投诉工单通过 12345 热线频频涌来」

**解法**：推行「**取送分离**」——商户出餐后由商场工作人员统一送到**外部取餐点**，骑手不进商场。效果：

- 日均减少骑手进入商场内部约 **400 人次**
- 商场内部因外卖配送引发的**警情下降 68%**

### 缺口就在这里

取送分离之后，**骑手全部集中在取餐点等餐**——他们最需要知道的恰恰是「**我的单好了没有**」。而取餐点上，现在什么也没有。

### 实用性的诚实评估

| 方面 | 判断 |
|---|---|
| **需求真实性** | ✅ **高**。取送分离正在多城推行，取餐点必然需要出餐信息 |
| **竞品情况** | ⚠️ 平台（美团/淘宝闪购）有自己的取餐系统，多走平台 App。**我们的生态位是"不绑定平台的独立屏"** |
| **目标客户** | 多平台混营的小店、没接平台系统的小店、商场统一取餐点 |
| **核心卖点** | **不联网、不绑平台、无月费、无账号、断电来电即恢复**——小店没有 IT 能力，网络故障也没人修 |
| **工程化差距** | 需要预留网络/云更新素材的接口（作为后续版本说明即可） |
| **演示可行性** | ✅ 笔记本串口工具发订单号，或按键模拟来单 |

> **建议的答辩口径**：不是替代平台系统，而是给"不接平台、不想联网"的商户一个**零运维的独立方案**。

## 三、产品形态

装在**取餐点**（或店门口）的一块屏。

| 屏幕分区 | 内容 | 数据源 | 对应要求 |
|---|---|---|---|
| **主区**（大字号格位） | **已出餐待取**的订单号；新号出现时**闪烁 + 高亮** | 串口 | 扩展①、④ |
| **副区** | **制作中**的订单号列表 | 串口 | 扩展① |
| **底部** | 提示文案**平滑滚动** | 片内字库实时渲染 | **扩展①（平滑滚动）** |
| **背景层** | 优惠画面 / 菜单图，按**转场**轮播并自适应缩放 | SD 卡 | 扩展②、③ |
| **角标** | 亮度 / 对比度**档位** OSD | — | **扩展④（OSD）** |
| **音频** | 背景音乐 + **频谱** | SD 卡 | 基础③、**扩展⑤** |

## 四、系统框图与数据流

```
                    ┌──────────────────────────────┐
  SD卡 ──SPI────────┤                              │
  (静态素材)        │    FPGA (安路 EG4S20)        │
                    │                              │
  串口 ──UART───────┤  · SPI 读取 + BMP 解析       ├──HDMI──→ 显示屏(含音频)
  (订单号/状态)     │  · SDRAM 帧缓存 + 双缓冲     │
                    │  · 多层并行合成              │
  按键 ─────────────┤  · 字库实时渲染 + 滚动       │
  (亮度/对比度)     │  · 缩放 / 转场 / OSD         │
                    │  · 音频滤波器组              │
                    └──────────────────────────────┘
```

**关键点：两路数据源在 FPGA 内汇合。** 静态素材走 SPI/SD 卡，动态订单走 UART，两者在像素流水线里被合成到同一帧。

## 六、合规性：UART 是不是"额外处理器"？

**不是。**

- UART 接收器是 FPGA **内部**的一段常规时序逻辑（约 50~80 行 Verilog），不是独立器件，更不是处理器
- 赛题允许「根据作品需要搭配外围电路或成品模块」，一个 USB-串口模块属于**外围电路**
- 赛题要求「所有算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」——**UART 自己写，正好满足这条**

> 建议在答辩时主动说明：**订单数据经串口进入 FPGA，由自主实现的接收逻辑解析后参与画面合成。**

---

## 七、FPGA 优势（三条都很实在）

1. **多源信息融合**——静态素材与动态订单两路实时合成，这是赛题点名的优势项
2. **确定性刷新**——订单号到达后**下一帧即上屏**（≤16.7ms），没有软件调度抖动，骑手不会看到"卡住的号"
3. **无操作系统**——营业 14 小时全程不死机；上电即出画面；断电来电立刻恢复

## 八、演示脚本

| 时间 | 操作 | 观众看到 |
|---|---|---|
| 0:00 | 上电 | **屏幕立刻亮起**（对比电脑开机几十秒） |
| 0:05 | 串口发送订单号 `0231` | 副区"制作中"出现 0231 |
| 0:15 | 再发 `0232`、`0233` | 号依次进入制作区 |
| 0:25 | 发送"0231 已出餐" | 0231 **跳到主区大字号格位并闪烁两下** |
| 0:35 | 按键调亮度 | 画面变亮，**右下角 OSD 显示档位** |
| 0:45 | 按键切优惠画面 | 菜单图**淡入淡出切换** |
| 0:55 | 背景音乐播放中 | 屏幕频谱条**随节奏起伏**，底部文案平滑滚动 |

> **一句话证明技术**：订单号从串口到屏幕**只用一帧**，而且两路数据（卡里的素材 + 串口来的号）是在 FPGA 里合成到同一帧的。
